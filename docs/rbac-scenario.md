# Path-based RBAC на всех 9 oauth-proxy: service2 + service2/admin

> Ветка: `feature/path-based-rbac`. Расширяет основной RND ([`oauth-proxy-rnd.md`](oauth-proxy-rnd.md))
> более сложным сценарием авторизации: не просто "пустить аутентифицированного",
> а path-based RBAC на одном домене — разные роли для корня и для `/admin`.
> Все 9 решений реализованы, подняты и проверены живым end-to-end тестированием
> (54 теста, все пройдены). Конфигурация и подробный README с полным выводом
> команд — в `rbac-scenario/<proxy>/`.

## 1. Постановка задачи

Из обсуждения с пользователем — требование сложнее базового сценария
основного RND:

- `service1.example.com` — доступ любому аутентифицированному пользователю.
  **Не пересобирался в этой ветке** — это ровно то, что уже реализовано и
  протестировано для всех 9 решений в основном стенде (`proxies/`).
- `service2.example.com` — доступ только роли **`Team2_Users`**.
- `service2.example.com/admin` — доступ только роли **`Team2_Admins`**.

Локально `service2.example.com` смоделирован как `service2.localhost`
(поддомены `*.localhost` резолвятся в 127.0.0.1 автоматически, RFC 6761,
без правки `/etc/hosts`).

## 2. Стенд

### 2.1. Общие компоненты (уже настроены)

- **Keycloak, realm `corp-sso`** — добавлены роли `Team2_Users`/`Team2_Admins`
  и 11 новых клиентов (по одному-два на решение, см. таблицу портов ниже).
- **Тестовые пользователи:**

  | Пользователь | Пароль | Роли |
  |---|---|---|
  | `team2user` | `Team2User12345!` | `Team2_Users` |
  | `team2admin` | `Team2Admin12345!` | `Team2_Users`, `Team2_Admins` |
  | `testuser` | `Test12345!` | `app-user` (без `Team2_*` — негативный тест) |

- **`rbac-scenario/service2-backend`** — общий backend без какой-либо
  авторизационной логики, переиспользуется всеми 9 реализациями:
  `/` отдаёт текст "область Team2_Users", `/admin` — "область Team2_Admins".
  Порт наружу не публикуется.
- **`scripts/test-oidc-login.sh`** — универсальный E2E-логин скрипт из
  основного RND, расширен переменными `EXPECT_TEXT` (искомая строка успеха)
  и `JAR_OUT` (сохранить cookie jar для последующих ручных запросов другими
  путями, например `/admin`) — обе использовались во всех 9 реализациях.

## 3. Сводная таблица решений

| Решение | Архитектура RBAC | Доп. сервисы | Декларативность | Ключевая находка |
|---|---|---|---|---|
| **gogatekeeper** | `resources: [{uri, roles}]` — нативно, один инстанс | Нет | Полностью декларативная (YAML) | `/admin/*` не матчит `/admin` без слэша — нужны оба правила |
| **Pomerium** | Несколько `routes` с одним `from`, разным `prefix`, `policy: claim/roles` | Нет | Полностью декларативная (YAML/PPL) | `claim/roles: <value>` работает как array-contains "из коробки"; порядок routes не важен |
| **Apache APISIX** | Два `route` + `openid-connect` + `serverless-pre-function` (Lua) на роль | Нет (доп. плагин в том же инстансе) | Частично (Lua-код для role-check) | Приоритет плагинов критичен (`_meta.priority`), иначе role-check выполняется раньше аутентификации |
| **oauth2-proxy** | Два инстанса (`--allowed-group` на весь инстанс) + nginx-роутинг по пути | +1 nginx, +1 oauth2-proxy | Нет (N ролей = N инстансов) | `--oidc-groups-claim` неявно требует OAuth-scope `groups` → `invalid_scope`, если такого client scope нет |
| **vouch-proxy** | vouch аутентифицирует + отдаёт claims-заголовок; RBAC — во front-прокси | Vouch не имеет своего RBAC — обязателен OpenResty/Lua (ванильный nginx `if` физически не может, см. §4) | Нет (Lua-код) | Нативный nginx `if` выполняется раньше `auth_request` (rewrite vs access фаза) — путь на ванильном nginx тупиковый |
| **Envoy** | 3 нативных фильтра: `oauth2` → `jwt_authn` → `rbac` (per-route) | Нет (все фильтры внутри Envoy) | Частично (декларативно, но ~140 строк raw-proto на 1 путь) | CSRF/PKCE-cookie фильтра всегда `Secure` — нужен TLS даже локально |
| **Traefik** | Два инстанса oauth2-proxy (как в oauth2-proxy-сценарии) + два router/middleware | +2 oauth2-proxy | Нет (N ролей = N инстансов) | Та же проблема `--oidc-groups-claim`→`groups` scope, что и у oauth2-proxy |
| **OpenResty** | Два `location`, Lua-проверка `id_token.roles` в каждом | Нет | Нет (Lua-код), но без внешних сервисов | Самое гибкое решение архитектурно — вся логика в одном процессе, без доп. инфраструктуры |
| **HAProxy** | Один auth-only oauth2-proxy (без `--allowed-group`) + HAProxy ACL проверяет `X-Auth-Request-Groups` по пути | +1 oauth2-proxy (только аутентификация) | Нет (ACL-код) | Единственный из "workaround"-подходов, где хватило ОДНОГО экземпляра auth-сервиса — роль проверяет сам балансировщик |

## 4. Детальный разбор по решениям

### 4.1. gogatekeeper — самый простой случай

Один инстанс, `resources` с двумя правилами (`/admin*` → `Team2_Admins`,
`/*` → `Team2_Users`). Никакой дополнительной инфраструктуры.

**Найдено и исправлено:** паттерн `/admin/*` не матчит литеральный путь
`/admin` без завершающего слэша — запрос проваливается в catch-all `/*` и
проходит с недостаточной ролью. **Подтверждено вживую и независимо
перепроверено координатором** ("голый" и `/admin/`-запрос от `team2user`
без роли `Team2_Admins` — оба корректно `403` после фикса, `200` до
фикса на "голом" пути). Практический вывод: на любой защищаемый "раздел"
нужны два правила — точный путь и `путь/*`.

Отдельно проверена (по прямому требованию задания) гипотеза "порядок правил
`resources` критичен, специфичное должно идти раньше catch-all" —
**эмпирически не подтвердилась** для gogatekeeper 4.11.0: движок матчинга
основан на `go-chi/chi` (радиксное дерево маршрутов), которое само находит
наиболее специфичный маршрут независимо от порядка объявления в YAML.
Специфичное-перед-общим тем не менее оставлено как defensive-практика —
недокументированная деталь текущей реализации может не сохраниться в других
версиях/форках.

Подробности: [`rbac-scenario/gogatekeeper/README.md`](../rbac-scenario/gogatekeeper/README.md).

### 4.2. Pomerium — декларативно, но с оговоркой по документации

Один инстанс, два `routes` с одинаковым `from` (`service2.localhost`),
разным `prefix` (`/admin` vs корень) и своей `policy` на каждый. Pomerium
сам матчит более специфичный `prefix` — в отличие от gogatekeeper, порядок
объявления `routes` подтверждённо не важен (проверено перестановкой).

**Ключевая находка:** официальная документация Pomerium Policy Language не
описывает явно семантику `claim/<name>: <value>` для claim-массивов (наш
`roles` — массив строк). Эмпирически подтверждено: простейший синтаксис
`claim/roles: Team2_Admins` работает сразу как "содержит значение", без
необходимости `has`/`in`.

Как и в основном стенде — TLS обязателен (Secure-флаг на CSRF-cookie
захардкожен), плюс отдельный `authenticate_service_url`-хост.

Подробности: [`rbac-scenario/pomerium/README.md`](../rbac-scenario/pomerium/README.md).

### 4.3. Apache APISIX — декларативно + немного Lua

Два `route`, оба с плагином `openid-connect`; ролевая проверка — отдельный
плагин `serverless-pre-function`, читающий `X-Userinfo` (base64 JSON,
который сам `openid-connect` кладёт апстриму) и сверяющий массив `roles`.

**Ключевая находка:** APISIX выполняет плагины по убыванию `priority`;
`serverless-pre-function` (по умолчанию 10000) без явного понижения
приоритета выполнился бы РАНЬШЕ `openid-connect` (~2599) — то есть role-check
видел бы ещё не существующий заголовок. Исправлено `_meta.priority: 2000`.
Независимо от gogatekeeper найдена та же проблема с `/admin` без слэша —
исправлено `uris: [/admin, /admin/*]`.

Подробности: [`rbac-scenario/apisix/README.md`](../rbac-scenario/apisix/README.md).

### 4.4. oauth2-proxy — самый честный "workaround"-случай

У oauth2-proxy `--allowed-group` действует на весь инстанс, не на путь.
Решение: два независимых инстанса (`--allowed-group=Team2_Users` и
`=Team2_Admins`), каждый со своим `--proxy-prefix` (иначе оба конкурировали
бы за один `/oauth2/callback`), плюс nginx, маршрутизирующий `/admin` к
admins-инстансу, остальное — к users-инстансу.

**Найдено и исправлено:** `--oidc-groups-claim=roles` заставляет oauth2-proxy
неявно добавить в запрос OAuth-scope `groups` — в realm, где роли приходят
напрямую через protocol mapper (без отдельного client scope `groups`),
Keycloak отвечает `invalid_scope`. Фикс: явный `--scope=openid email profile`.

Побочный эффект архитектуры: у пользователя фактически две независимые
cookie-сессии на одном домене (по одной на инстанс); переход с `/` на
`/admin` — это второй, невидимый пользователю, OIDC-flow (SSO-сессия
Keycloak переиспользуется без повторного пароля, но роль проверяется
заново и независимо).

Подробности: [`rbac-scenario/oauth2-proxy/README.md`](../rbac-scenario/oauth2-proxy/README.md).

### 4.5. vouch-proxy — тупик без Lua

У vouch-proxy нет policy-движка вообще — только `headers.claims: [roles]`,
кладущий роли в заголовок `X-Vouch-IdP-Claims-Roles` (формат — Go-слайс
через пробел, `[Team2_Users Team2_Admins]`, НЕ JSON). RBAC пришлось
целиком вынести во front-прокси.

**Главная находка:** классический паттерн "`auth_request` +
`auth_request_set` + `if`" для проверки РОЛИ на ванильном nginx **физически
не работает** — директива `if` выполняется в фазе `rewrite`, которая идёт
раньше фазы `access`, где отрабатывает `auth_request`; на момент проверки
`if` переменная с ролями ещё пуста. Второй `auth_request` в одном location
nginx явно запрещает. Единственный рабочий выход — `access_by_lua_block`
(OpenResty), то есть **связка "vouch-proxy + ванильный nginx" не может
делать path-based RBAC без модуля скриптования**. Практический вывод:
выбор vouch-proxy для подобной задачи фактически обязывает перейти на
OpenResty — с лишним сетевым прыжком к vouch-proxy и без выгоды от его
широкого списка провайдеров (Keycloak и так поддержан напрямую в
lua-resty-openidc).

Вторая находка: `cookie.domain: localhost` (как в основном стенде) на хосте
`service2.localhost` приводит к тому, что curl/браузер отклоняют cookie как
потенциальный public suffix — `cookie.domain` обязан точно совпадать с
фактическим hostname.

Подробности: [`rbac-scenario/vouch-proxy/README.md`](../rbac-scenario/vouch-proxy/README.md).

### 4.6. Envoy — сработало с первой рабочей конфигурации, но дорогой ценой

Цепочка из трёх нативных фильтров: `oauth2` (аутентификация) →
`jwt_authn` (повторная валидация JWT + вынос `roles` в dynamic metadata) →
`rbac` (per-route policy через `typed_per_filter_config`, `list_match.one_of`
по metadata). Route `/admin` идёт раньше catch-all `/`.

Обе найденные проблемы — инфраструктурные, не архитектурные: cookie
oauth2-фильтра всегда `Secure` (та же история, что у Pomerium — TLS
обязателен), и приватный ключ сертификата с правами `600` недоступен
процессу Envoy (uid 101 в контейнере) — `chmod 644` решил, но
диагностическое сообщение Envoy (`Failed to load incomplete private key`)
вводило в заблуждение (звучит как "повреждённый файл", а не "нет доступа").

**Итог: все 6 тестов прошли с первой рабочей конфигурации** (после починки
TLS/прав) — связка технически работает полностью нативно, без единого
внешнего сервиса. Цена — ~140 строк verbose raw-proto YAML на один путь с
двумя ролями, deprecated API (`Principal.metadata`), и JWT валидируется
дважды (неявно в oauth2-фильтре, явно в jwt_authn).

Подробности: [`rbac-scenario/envoy/README.md`](../rbac-scenario/envoy/README.md).

### 4.7. Traefik — тот же паттерн, что oauth2-proxy

Ровно та же архитектура, что у oauth2-proxy (два инстанса на роль), только
маршрутизацию делает Traefik (`PathPrefix` + `forwardAuth` на разные
инстансы вместо nginx). Найдена та же проблема `--oidc-groups-claim` →
неявный scope `groups` → `invalid_scope`, тот же фикс (`--scope`).

Ограничения идентичны oauth2-proxy-сценарию: N ролей = N инстансов, две
независимые cookie-сессии на одном домене (перезаписывают друг друга по
имени/пути, что может путать при отладке, хотя не ломает функциональность).

Подробности: [`rbac-scenario/traefik/README.md`](../rbac-scenario/traefik/README.md).

### 4.8. OpenResty — самое гибкое, но без страховки декларативности

Два `location`, в каждом — `access_by_lua_block` с проверкой роли в массиве
`id_token.roles`. Единственное решение, где НЕ понадобилась вообще никакая
дополнительная инфраструктура (ни второй инстанс, ни внешний сервис).

Подтверждено: одна и та же сессия (`lua-resty-session`, `Path=/`) работает
для обоих `location` без повторного логина — переход на `/admin` просто
восстанавливает сессию из cookie и сразу идёт к проверке роли.

Обратная сторона гибкости: никакой валидации конфигурации на старте — в
отличие от `resources`/`policy` у gogatekeeper/Pomerium, ошибка в Lua-коде
проявится только в рантайме на конкретном запросе.

Подробности: [`rbac-scenario/nginx-openresty/README.md`](../rbac-scenario/nginx-openresty/README.md).

### 4.9. HAProxy — единственный "workaround", обошедшийся одним инстансом

В отличие от oauth2-proxy/Traefik-сценариев, здесь понадобился только ОДИН
auth-only oauth2-proxy (без `--allowed-group`) — он лишь аутентифицирует и
возвращает `X-Auth-Request-Groups`; финальное ролевое решение по пути
принимает сам HAProxy через ACL (`-m sub` на содержимом заголовка).

Формат заголовка подтверждён эмпирически: список ролей через запятую без
пробелов (`Team2_Users,Team2_Admins`). Это архитектурно самый экономный из
"workaround"-подходов по числу процессов, но ACL-синтаксис менее читаем,
чем декларативный список правил, и `-m sub` (подстрочный матч) в проде
стоит заменить на `-m reg` с границами слова во избежание ложных
совпадений между похожими именами ролей (`Team2_Admins` vs
`Team2_Admins_Readonly`).

Подробности: [`rbac-scenario/haproxy/README.md`](../rbac-scenario/haproxy/README.md).

## 5. Общие выводы

**Два решения дают полностью декларативный path-based RBAC без единой
дополнительной строки кода и без лишних сервисов: gogatekeeper и Pomerium.**
Это подтверждает и усиливает рекомендацию основного RND-отчёта. Разница
между ними для этой конкретной задачи:

- **gogatekeeper** — синтаксис проще (`resources: [{uri, roles}]`), но
  порядок правил из документации разных источников не всегда однозначен
  (для этой версии оказался не критичен — движок сам находит специфичный
  маршрут), и есть реальная ловушка с завершающим слэшем.
- **Pomerium** — чуть более многословный YAML (policy-блок вместо
  плоского списка ролей), зато официально документированное
  longest-prefix-match поведение routes избавляет от вопроса порядка
  правил, и policy-язык мощнее (можно комбинировать claim/domain/device
  и т.п. в одном правиле), но ценой обязательного TLS и отдельного
  authenticate-хоста.

**Envoy и APISIX дают декларативный/полудекларативный RBAC ценой заметно
большей сложности конфигурации** — оба сработали и прошли все тесты, но
Envoy-конфиг на порядок многословнее (raw-proto YAML), а APISIX требует
понимания порядка выполнения плагинов (не lock-in ошибка, а
недекларативная Lua-вставка).

**oauth2-proxy и Traefik решают задачу одинаковым "размножением
инстансов"-паттерном** — рабочим, но с растущей линейно операционной
сложностью (N ролей = N процессов + N Keycloak-клиентов) и двумя
независимыми cookie-сессиями на одном домене.

**HAProxy — единственный "workaround", которому хватило одного
auth-сервиса** благодаря тому, что сам балансировщик достаточно
программируем (ACL) для финального ролевого решения — паттерн стоит
рассмотреть как более экономную альтернативу oauth2-proxy/Traefik
multi-instance подходу, если HAProxy уже стандарт в компании.

**vouch-proxy — единственное решение, для которого path-based RBAC в
исходной, "рекомендованной" конфигурации (ванильный nginx) оказался
физически невозможен** — только переход на OpenResty/Lua во front-слое
даёт рабочий результат, что фактически нивелирует изначальную простоту
vouch-proxy как выбора для такой задачи.

**OpenResty — самое архитектурно гибкое решение** (никакой дополнительной
инфраструктуры вообще), но целиком полагается на корректность
написанного вручную Lua-кода без какой-либо валидации на старте — та же
позиция, что и в основном RND-отчёте, только теперь подтверждённая на
конкретном RBAC-кейсе.

### Обновлённая рекомендация (дополняет `oauth-proxy-rnd.md`, раздел 7.1)

Для сценария "разные роли на разных путях одного домена" в порядке
приоритета:

1. **gogatekeeper** или **Pomerium** — если нужен чисто декларативный RBAC
   без дополнительного кода/инстансов. Pomerium предпочтителен при
   множестве приложений/доменов с одного control plane и при готовности к
   обязательному TLS; gogatekeeper — при более простом, "одно приложение —
   один инстанс" размещении.
2. **HAProxy (ACL-подход)** — если HAProxy уже стандарт балансировки в
   компании и не хочется размножать auth-инстансы на каждую роль.
3. **APISIX** — если уже используется как API-шлюз и приемлема
   Lua-вставка с пониманием приоритетов плагинов.
4. **OpenResty** — при наличии Lua-экспертизы в команде и желании
   максимальной гибкости без внешней инфраструктуры.
5. **Envoy** — только если Envoy уже стандартизован как data plane;
   в остальных случаях сложность конфигурации не окупается (для прода
   разумнее Envoy Gateway с `SecurityPolicy`/`AuthorizationPolicy` CRD
   поверх этого же паттерна).
6. **oauth2-proxy / Traefik (multi-instance)** — рабочий, но самый
   многословный по числу движущихся частей вариант; выбирать, если
   команда уже стандартизовала именно этот стек и не готова добавлять
   HAProxy/gogatekeeper/Pomerium ради одной задачи.
7. **vouch-proxy** — не рекомендуется для path-based RBAC: в исходной
   конфигурации задача нерешаема, а решение через OpenResty/Lua
   обесценивает изначальную простоту выбора vouch-proxy.
