h1. 1. Постановка задачи

В компании внедрён Keycloak как корпоративный SSO (OpenID Connect / OAuth2).
Часть внутренних и legacy-приложений не умеет само по себе быть OIDC
Relying Party (нет встроенной поддержки OpenID Connect / SAML). Требуется
универсальный "OAuth-прокси" слой, который:

* принимает незалогиненный HTTP-запрос к защищённому приложению;
* отправляет пользователя на аутентификацию в Keycloak (Authorization Code Flow);
* после успешного логина создаёт собственную сессию (cookie) и пропускает
  запрос к приложению, опционально прокидывая identity (email, username,
  роли/группы) через HTTP-заголовки;
* самостоятельно продлевает сессию (refresh token), пока валиден refresh
  token / SSO-сессия в Keycloak.

Цель RND — сравнить основные open-source реализации такого слоя и дать
рекомендацию по выбору, схеме внедрения и эксплуатации.

h1. 2. Требования к OAuth-Proxy

h2. 2.1. Функциональные требования

||#||Требование||Комментарий||
|Ф1|Полная поддержка Authorization Code Flow с Keycloak (OIDC)|Обязательно; Implicit/Hybrid не нужны|
|Ф2|OIDC Discovery (`/.well-known/openid-configuration`)|Снижает конфигурационные ошибки и упрощает ротацию ключей подписи (JWKS)|
|Ф3|Автоматическое обновление токена (refresh token) без повторного логина пользователя|Критично для UX — сессии не должны рваться каждые 5 минут по access-token TTL|
|Ф4|Проброс identity в апстрим через заголовки (email, username, sub, роли/группы)|Приложение должно получать данные о пользователе, не разбирая JWT самостоятельно|
|Ф5|Возможность грубой авторизации (allow-list по email/домену/группе/роли)|Минимум — pre-auth фильтр до захода в приложение|
|Ф6|Поддержка нескольких защищаемых приложений/доменов с одного инстанса|Важно для операционных издержек — не поднимать инстанс на каждое приложение|
|Ф7|Логаут (в т.ч. RP-initiated logout / очистка сессии на стороне Keycloak)|Желательно, не всегда критично для внутренних инструментов|
|Ф8|Прозрачная работа с WebSocket / SSE / стриминговыми апстримами|Актуально не для всех приложений, но стоит проверять отдельно|

h2. 2.2. Нефункциональные требования

||#||Требование||Комментарий||
|Н1|Активная поддержка / сообщество, понятный security-процесс (CVE, advisories)|Прокси терминирует аутентификацию — обязана быстро закрывать уязвимости|
|Н2|Горизонтальное масштабирование, отсутствие sticky-session требований|Хранение сессии не в памяти процесса (cookie или внешний stateful store)|
|Н3|Низкий overhead по latency и ресурсам|Прокси в пути каждого запроса|
|Н4|Простота конфигурации "как код" (YAML/labels), пригодность для GitOps/CI-CD|
|Н5|Наблюдаемость: метрики (Prometheus), структурные логи, health-пробы|
|Н6|Безопасное хранение секретов клиента (не в открытом виде в репозитории)|
|Н7|Совместимость с текущим стеком балансировки/ingress компании|Envoy/Traefik/Nginx/HAProxy — если один из них уже стандарт, это сильно влияет на выбор|

h1. 3. Архитектурные паттерны

В индустрии для этой задачи используется четыре паттерна:

# *Выделенный OAuth reverse-proxy* — отдельный сервис сам является upstream'ом
для клиента (браузера) и проксирует уже аутентифицированный запрос к
приложению. Примеры: *oauth2-proxy*, *gogatekeeper*.
# *Auth-subrequest ("forward auth")* — балансировщик/веб-сервер перед каждым
запросом делает внутренний подзапрос к отдельному auth-сервису; тот
возвращает 200/202 (пустить) или 401/редирект (не пустить). Сам auth-сервис
не проксирует основной трафик. Примеры: nginx `auth_request` + *oauth2-proxy*
или *vouch-proxy*; Traefik `ForwardAuth` + *oauth2-proxy*; HAProxy + Lua
(`haproxy-auth-request`) + *oauth2-proxy*.
# *Нативный фильтр балансировщика* — OIDC/OAuth2-логика встроена прямо в
процесс балансировщика, без дополнительного сетевого прыжка и отдельного
сервиса. Примеры: нативный OAuth2 HTTP-фильтр *Envoy*, *OpenResty +
lua-resty-openidc*, коммерческие *NGINX Plus* (нативный OIDC-модуль,
R34+) и *HAProxy Enterprise* (OIDC/SSO-модуль).
# *Коммерческое расширение балансировщика* — то же самое, что (3), но как
платная функция вендора (Traefik Hub, NGINX Plus, HAProxy Enterprise).

{tip}Паттерны (1) и (2) — по сути один и тот же auth-сервис (oauth2-proxy),
просто с разным режимом работы (`--upstream` полноценный прокси vs
`--upstream=static://202` только для forward-auth). Это ключевая причина,
почему oauth2-proxy показал наибольшую гибкость в RND — один и тот же
инструмент закрывает оба паттерна.{tip}

h1. 5. Детальный разбор решений

h2. 5.1. oauth2-proxy

{tip:title=Итог RND}Наиболее сбалансированное и низкорисковое решение из
проверенных. Рекомендуется как основной вариант.{tip}

*Плюсы:*
* Принят в CNCF Sandbox (октябрь 2025) — сильный сигнал зрелости и
  долгосрочной поддержки, регулярные security-релизы (v7.15.x).
* Широкий список провайдеров, включая generic OIDC — переиспользуем один и
  тот же инструмент и для Keycloak, и для внешних SaaS-провайдеров при
  необходимости.
* Единственный из рассмотренных инструментов одинаково хорошо работает и как
  самостоятельный reverse-proxy, и как backend для `auth_request`/`ForwardAuth`
  (режим `--upstream=static://202`) — использовался в RND именно так для
  связок с Traefik и HAProxy.
* Известный, задокументированный паттерн интеграции с ingress-nginx в
  Kubernetes.

*Минусы:*
* Узкая функциональная область: чистая аутентификация + грубая авторизация
  (allowed groups/emails/claims), нет ABAC/policy-движка.
* Сложные multi-upstream/multi-domain сценарии требуют нескольких инстансов
  либо аккуратного path-based роутинга на уровне балансировщика.

*Проверено в RND:* полный login-flow, claims (`email`, `preferred_username`,
`roles`) корректно проброшены в заголовках `X-Auth-Request-*` апстриму.
Конфигурация: {{proxies/oauth2-proxy/docker-compose.yml}}.

h2. 5.2. gogatekeeper

*Контекст:* официальный Keycloak Gatekeeper (ранее — Louketo Proxy) объявлен
Red Hat/Keycloak team устаревшим, репозиторий заархивирован в декабре 2020.
*gogatekeeper* — независимое community-продолжение того же кодовой базы, не
аффилировано с проектом Keycloak.

*Плюсы:*
* Самая богатая из проверенных решений модель авторизации "из коробки":
  role/claim/group matching (в т.ч. `require-any-role`), нативная интеграция
  с OPA и Keycloak UMA.
* Шире протокольная поддержка: mTLS, WebSocket/SSE проксирование, TCP-туннели
  через HTTP CONNECT, FIPS-режим.
* Спроектирован специально под Keycloak — большинство "keycloak-специфичных"
  практик (PKCE, token exchange) поддержаны нативно.

*Минусы:*
* Существенно меньше community и экосистема, чем у oauth2-proxy; не под
  CNCF; крупных публичных enterprise-адоптеров не найдено.
* Модель "один upstream на инстанс" усложняет защиту множества приложений.
* На момент RND (сентябрь 2026) стабильный релиз 5.0.0 ещё не вышел (RC10) —
  возможны изменения конфигурации между RC и финальным релизом.

*Проверено в RND:* полный login-flow. *Найденная особенность конфигурации:*
опция `enable-default-deny: true` включена по умолчанию и конфликтует с
явным правилом `resources: [{uri: "/*", ...}]` — процесс падает в
crash-loop с ошибкой {{you've enabled default deny and at the same time
defined own rules for /*}}. Решение: явно выставить `enable-default-deny:
false`, если используется собственное catch-all правило (см.
{{proxies/gogatekeeper/config.yml}}).

h2. 5.3. vouch-proxy

*Плюсы:*
* Простой единый Go-бинарник, низкое потребление ресурсов.
* Широкий список поддерживаемых провайдеров "из коробки" (Google, GitHub,
  Okta, Azure AD, ADFS, AWS Cognito, generic OIDC и др.), включая готовый
  пример конфигурации именно под Keycloak.
* Явное разделение browser-facing endpoint (`auth_url`) и backend-only
  endpoints (`token_url`, `user_info_url`) в конфиге — архитектурно честнее,
  чем единый `issuer-url` у oauth2-proxy/gogatekeeper (хотя именно это и
  стало источником проблемы, см. ниже).

*Минусы:*
* Небольшая сопровождающая команда, менее формализованный release-процесс
  (только git-теги, без дисциплины GitHub Releases).
* Нет OIDC discovery — endpoints задаются вручную, что увеличивает риск
  рассинхронизации конфигурации при смене realm/провайдера.
* Нет встроенного policy-движка — авторизация только через заголовки claims
  на стороне приложения.
* Хранение сессии — только cookie (подписанный JWT), без Redis/внешнего
  стора.
* Мультидомен ограничен единым parent-доменом (cookie domain scoping).

*Проверено в RND, найдена и воспроизведена реальная проблема:* при разных
hostname для `auth_url` (browser-facing) и `token_url`/`user_info_url`
(backend) получили `401 unexpected end of JSON input` на этапе получения
userinfo. Причина: Keycloak привязывает claim `iss` в выданном токене к
тому hostname, с которого браузер инициировал `/auth`, а не к hostname,
которым backend впоследствии вызывает `/token`/`/userinfo` — при
рассинхронизации токен не проходит валидацию issuer'а на `/userinfo`.
Исправлено приведением всех трёх endpoint'ов к одному hostname
(см. {{proxies/vouch-proxy/config.yml}}). *Это системная особенность
Keycloak, а не баг vouch-proxy — актуальна для любого решения, где OIDC
endpoints задаются вручную, а не через единый discovery/issuer-url.*

h2. 5.4. Envoy — нативный OAuth2-фильтр (`envoy.filters.http.oauth2`)

*Плюсы:*
* Работает внутри процесса Envoy — нет отдельного сервиса и лишнего
  сетевого прыжка, минимальные накладные расходы по latency.
* Единая точка авторизации для гетерогенного стека сервисов, если Envoy уже
  используется как data plane (service mesh, API gateway).
* Активно развивается как часть ядра Envoy (CNCF Graduated); PKCE и
  настройка `SameSite` добавлены в v1.34.

*Минусы:*
* Нет встроенного OIDC discovery — authorization/token endpoints
  прописываются вручную; конфигурация verbose (raw proto), нет обёрток без
  дополнительных инструментов (Envoy Gateway, Istio).
* Нет встроенного RBAC — только аутентификация; авторизация собирается
  дополнительной связкой `jwt_authn`/`rbac` фильтров.
* Per-route OAuth2-конфигурация полностью заменяет (replace), а не
  дополняет (merge) конфиг уровня listener — легко ошибиться при
  разнородных правилах для разных route.
* Секреты (HMAC для подписи cookie, client_secret) требуют полноценного SDS
  (control-plane/Vault) в проде — инлайн-файлы (как в RND-стенде) не
  подходят для эксплуатации.

*Проверено в RND:* полный login-flow, включая автоматическое добавление
PKCE самим фильтром. *Грабли:* при использовании SDS-секретов Envoy
требует секцию `node: {id, cluster}` в bootstrap-конфиге, иначе падает с
ошибкой `node 'id' and 'cluster' are required`.
Конфигурация: {{proxies/envoy/}}.

*Рекомендация:* нативный фильтр целесообразен только если Envoy уже —
стандартный data plane компании (Envoy Gateway, Istio, Gloo Edge и т.п.);
Envoy Gateway с версии 1.8 даёт `SecurityPolicy` CRD, которая генерирует
этот фильтр автоматически и снимает часть verbose-конфигурации. Для
"голого" Envoy без такой обвязки эксплуатационная сложность заметно выше,
чем у oauth2-proxy.

h2. 5.5. Traefik OSS + ForwardAuth + oauth2-proxy

*Важное уточнение:* у Traefik OSS (community edition) *нет* нативного OIDC
middleware — это исключительно платная функция *Traefik Hub*. Стандартный
open-source паттерн — `ForwardAuth` middleware к внешнему auth-сервису
(в RND использован oauth2-proxy).

*Плюсы:*
* Разделение ответственности: Traefik занимается роутингом, отдельный
  сервис — аутентификацией; тот же auth-сервис можно переиспользовать перед
  другими балансировщиками.
* Декларативный чейнинг middleware упрощает per-route/per-domain политику.
* Существуют зрелые community-плагины (*traefik-oidc-auth*, *traefikoidc*),
  дающие нативный OIDC discovery/PKCE/refresh/RBAC прямо в Traefik без
  отдельного сервиса — не разворачивались в этом RND, но заслуживают
  отдельного pilot, если критична экономия на дополнительном сервисе.

*Минусы:*
* Полноценный "из коробки" OIDC UX официально есть только в платном Traefik
  Hub.
* В OSS-варианте всё равно нужен отдельный stateful-сервис (oauth2-proxy) —
  лишняя движущаяся часть и хранилище сессий.
* Community-плагины (Yaegi/WASM) исторически менее зрелые и с меньшим
  adoption, чем mainstream-инструменты.

*Проверено в RND, ключевая грабля:* ForwardAuth нельзя направлять на
`/oauth2/auth` эндпоинт oauth2-proxy — он предназначен для nginx
`auth_request` и всегда отдаёт "голый" 401 без `Location`-заголовка, а
Traefik ретранслирует этот 401 как есть клиенту (в т.ч. с middleware
`errors` — она подменяет только тело, не код). Правильный паттерн —
направлять ForwardAuth на корень oauth2-proxy (`/`), запущенного с
`--upstream=static://202`: при валидной сессии он отдаёт 202 (Traefik
пропускает, копируя `authResponseHeaders`), при отсутствии сессии — 302 на
Keycloak, который Traefik успешно ретранслирует. Конфигурация:
{{proxies/traefik/}}.

h2. 5.6. Nginx / OpenResty

h3. (a) nginx OSS + `auth_request` + oauth2-proxy/vouch-proxy

Отраслевой стандарт де-факто (используется, в частности, ingress-nginx в
Kubernetes через аннотацию `auth-url`). Модуль
`ngx_http_auth_request_module` стабилен с 2013 года, входит в большинство
дистрибутивных и Docker-сборок nginx. Плюсы/минусы идентичны выбранному
auth-сервису (см. 5.1/5.3) плюс дополнительный сетевой прыжок на subrequest.
Рекомендуется, если nginx уже стандарт балансировки в компании — самый
низкий эксплуатационный риск среди auth_request-паттернов.

h3. (b) OpenResty + lua-resty-openidc

*Плюсы:*
* Вся OIDC-логика выполняется прямо в воркерах OpenResty — нет отдельного
  сервиса и сетевого прыжка.
* Максимальная гибкость: authz-логика — произвольный Lua-код, discovery и
  JWKS кэшируются в shared dict.
* Глубокая интеграция с экосистемой OpenResty/Kong/APISIX, если она уже
  используется как API-шлюз.

*Минусы:*
* Требует OpenResty вместо ванильного nginx (кастомная сборка образа) и
  Lua-экспертизы в команде эксплуатации.
* Темп релизов заметно замедлился (последний тег v1.9.1 — сентябрь 2024),
  проект по сути держится на одном активном сопровождающем — риск "bus
  factor".
* Версии транзитивных Lua-зависимостей (например, `lua-resty-session`)
  могут быть несовместимы с конкретным базовым образом/версией OpenSSL —
  реальный операционный риск при апгрейдах.

*Проверено в RND, найдена и воспроизведена проблема сборки:* `opm`
по умолчанию подтягивает `lua-resty-session` v4.1.5, использующую
HKDF-деривацию ключей через `resty.openssl`; на образе
`openresty/openresty:1.25.3.1-alpine-fat` это падает рантайм-ошибкой
(`attempt to call field 'new' (a nil value)`), т.к. связанная в образе
OpenSSL-обвязка не поддерживает нужный API. Исправлено фиксацией версии
`lua-resty-session=3.10` (см. {{proxies/nginx-openresty/Dockerfile}}). Также
`opm` разрешил `lua-resty-openidc` в версию 1.7.5, а не актуальную 1.9.1 —
реестр `opm` отстаёт от GitHub-релизов, для актуальной версии нужна ручная
установка через luarocks/git.

h3. (c) NGINX Plus — нативный OIDC-модуль (коммерческий, F5)

До релизной линейки R34 (2025) OIDC на NGINX Plus реализовывался через
community-референс на njs (`nginxinc/nginx-openid-connect`, всё ещё
существует, но считается legacy-путём). С *R34* добавлен нативный C-модуль
(`ngx_http_oidc_module`), упростивший конфигурацию до нескольких директив
(issuer URL, автодискавери). *R35* добавил RP-initiated logout, директиву
`userinfo` и модуль `ngx_http_auth_require_module` для RBAC по
`$oidc_claim_*`. *R36* добавил Front-Channel Logout 1.0 и автоматический
PKCE. Плюсы — официальная поддержка/SLA, нативная производительность без
subrequest/Lua overhead, минимальный конфиг. Минусы — платная подписка,
вендор-лок, часть возможностей доступна только в поздних релизах (R35+).
*Не разворачивался в этом RND* (требует лицензии), приведён для полноты
сравнения как готовая коммерческая альтернатива.

h2. 5.7. HAProxy

h3. (a) HAProxy OSS + Lua auth-request + oauth2-proxy

У open-source HAProxy нет полноценного встроенного OIDC login flow (только
конвертеры `jwt_verify`/`jwt_header_query` для проверки подписи уже
имеющегося JWT). Практический паттерн, аналогичный nginx `auth_request`, —
Lua-скрипт (в духе `TimWolla/haproxy-auth-request`), делающий auth-subrequest
к отдельному инстансу oauth2-proxy.

*Плюсы:* лёгкий вес, полный контроль на уровне конфигурации ACL, хорошо
сочетается с уже развёрнутым oauth2-proxy.

*Минусы:* нет единого канонического community-решения (несколько
разрозненных проектов разной активности и качества); требует кастомной
сборки образа с Lua-рантаймом и ручной установки зависимостей — ни одна из
частей (`haproxy-auth-request.lua`, `haproxy-lua-http`, `json.lua`) не
публикуется как готовый пакет.

*Проверено в RND, полный E2E успешно пройден, включая проброс identity
заголовков.* Найденные грабли:
* HAProxy не прерывает выполнение остальных `http-request` правил того же
  frontend после `use_backend` — без явных условий `unless
  is_oauth2_path`/`!is_oauth2_path` на каждом правиле возникает бесконечный
  redirect-loop на `/oauth2/start`.
* `lua-prepend-path` обязателен, иначе Lua ищет подключаемые модули от cwd
  процесса, а не от каталога скрипта.
* `haproxy-lua-http` нормализует имена заголовков ответа к нижнему регистру
  — обращение к ним по имени в оригинальном регистре (как в некоторых
  примерах README) не сработает без явной диагностики.

Конфигурация: {{proxies/haproxy/}}.

h3. (b) HAProxy Enterprise — модуль OpenID Connect (SSO), коммерческий

Официальный модуль HAProxy Technologies (требует HAProxy Enterprise
3.2r1+), поддерживает полный Authorization Code Flow, discovery, refresh
tokens, cookie-сессии с ротацией секрета, алгоритмы RS256/ES256/PS256/HS256.
Задокументированы примеры для Microsoft Entra ID и Okta. Явной готовой
поддержки multi-domain session sharing или RBAC/claims-enforcement "из
коробки" в публичной документации не найдено — судя по всему, реализуется
дополнительной конфигурацией. *Не разворачивался в этом RND* (требует
лицензии), приведён для полноты сравнения.

h1. 6. Типовые грабли внедрения (обнаружены практически в рамках RND)

{warning:title=Расхождение hostname Keycloak между браузером и backend}
Если конфигурация решения позволяет задавать OIDC endpoints раздельно
(browser-facing authorize endpoint vs backend token/userinfo endpoints —
как в vouch-proxy, или ручная настройка у Envoy), они *обязаны* указывать
на один и тот же hostname Keycloak. Keycloak привязывает claim `iss` в
выданном токене к hostname, с которого браузер инициировал `/auth`;
последующий вызов `/token` или `/userinfo` с *другого* hostname получит
`401 invalid_token` / пустое тело ответа, т.к. issuer не совпадёт.
В проде это решается единым публичным DNS-именем Keycloak, одинаково
резолвящимся и для пользовательских браузеров, и для backend-сети прокси
(в т.ч. через split-horizon DNS, если backend и клиенты в разных сетях).
Решения с единым `issuer-url`/`discovery-url` (oauth2-proxy, gogatekeeper)
структурно защищены от этой ошибки — ещё один аргумент в их пользу.
{warning}

{warning:title=Default-deny vs явные правила (gogatekeeper)}
`enable-default-deny: true` (значение по умолчанию) конфликтует с
собственным catch-all правилом `resources: [{uri: "/*"}]` — процесс не
стартует. Явно выставляйте `enable-default-deny: false`, если задаёте
собственные правила, покрывающие все пути.
{warning}

{warning:title=oauth2-proxy как ForwardAuth-backend}
Endpoint `/oauth2/auth` предназначен для nginx `auth_request` (всегда
возвращает "голый" 401 без `Location`). Для Traefik `ForwardAuth` (и
аналогичных paradigm, где сам балансировщик должен получить редирект на
логин) нужно направлять проверку на корень oauth2-proxy, запущенного с
`--upstream=static://202` — тогда при отсутствии сессии в ответе будет
полноценный 302 на Keycloak.
{warning}

{warning:title=Envoy SDS требует node.id/node.cluster}
При конфигурации HMAC/client_secret через SDS (обязательно для прода) в
bootstrap-конфиге Envoy должна присутствовать секция `node: {id, cluster}`,
иначе процесс падает с ошибкой валидации конфигурации при старте.
{warning}

{warning:title=Версии транзитивных зависимостей в кастомных Lua/OpenResty-сборках}
`lua-resty-session` v4+ требует HKDF-поддержку в связанном OpenSSL, которая
может отсутствовать в конкретном базовом образе — приводит к рантайм-ошибке
уже в проде на реальном трафике, если не закреплена версия зависимости.
Аналогичный риск справедлив для любых кастомных Lua-сборок (HAProxy, OpenResty).
{warning}

h1. 7. Рекомендации

h2. 7.1. Выбор решения

# *Основная рекомендация — oauth2-proxy*, в режиме reverse-proxy для
  выделенных приложений и в режиме `ForwardAuth`/`auth_request`-backend
  там, где уже есть Traefik/nginx/HAProxy. Наименьший операционный риск,
  лучшая поддержка сообществом (CNCF Sandbox), единый инструмент закрывает
  оба архитектурных паттерна — не нужно поддерживать два разных стека.
# *Если нужна более гранулярная авторизация "из коробки"* (roles/claims/
  OPA/UMA) и команда готова мириться с меньшим community — рассмотреть
  *gogatekeeper*, но дождаться стабильного релиза 5.0.0 перед вводом в прод
  (на момент RND — release candidate).
# *Если в компании уже стандартизован Envoy как data plane* (service mesh,
  Envoy Gateway/Istio) — использовать нативный OAuth2-фильтр *через Envoy
  Gateway `SecurityPolicy`* (не "голый" Envoy — verbose-конфигурация
  избыточно сложна для ручного сопровождения).
# *Если в компании уже есть коммерческая подписка* NGINX Plus или HAProxy
  Enterprise — их нативные OIDC-модули дают наименьшую операционную
  сложность и официальный SLA; экономически оправданы, если подписка уже
  куплена по другим причинам (LB/WAF-функциональность).
# *Не рекомендуется на старте* — vouch-proxy (малое community, нет
  discovery, ограниченный RBAC) и связка HAProxy OSS + Lua (нет
  канонического community-пакета, высокая стоимость поддержки
  кастомной Lua-сборки) — только если есть специфичная причина
  (например, HAProxy уже глубоко кастомизирован под Lua в компании).
# *Не рекомендуется* — OpenResty + lua-resty-openidc для новых внедрений,
  если нет уже существующей экспертизы OpenResty/Kong/APISIX в команде:
  темп поддержки библиотеки замедлился, риск bus factor, требуется
  Lua-экспертиза для сопровождения.

h2. 7.2. Развёртывание

* Все секреты клиентов (client_secret, cookie/HMAC-ключи шифрования сессии)
  — только через секрет-менеджер (Vault/Kubernetes Secrets/SOPS), никогда
  в открытом виде в git. В тестовом стенде RND секреты лежат в открытом виде
  намеренно — для прод-конфигурации это неприемлемо.
* TLS обязателен end-to-end: браузер → прокси (HTTPS) и, где это возможно,
  прокси → Keycloak. В RND-стенде HTTP используется только для локальной
  проверки.
* Для каждого защищаемого приложения — отдельный OIDC-клиент в Keycloak
  (или как минимум отдельный client per security-домен), а не один общий
  клиент на все приложения — иначе один скомпрометированный
  access/refresh-токен даёт доступ ко всем сервисам за прокси.
* Redirect URI клиента в Keycloak должен быть точным (без wildcard, если
  Keycloak/политика безопасности это позволяет отключить) и обязан совпадать
  ровно с тем, что настроено на прокси.
* Единое DNS-имя Keycloak для браузеров и backend-сети прокси (см.
  предупреждение в разделе 6) — заложить на этапе проектирования сети, а не
  чинить постфактум.

h2. 7.3. Эксплуатация

* Мониторинг: экспортировать метрики прокси (там, где они есть — у
  oauth2-proxy, Envoy, Traefik) в Prometheus; отдельно отслеживать долю
  401/403 и латентность auth-subrequest — рост может сигнализировать о
  проблемах с Keycloak или истекающих сертификатах.
* Ротация client_secret — регламентировать периодичность (например, раз в
  6-12 месяцев) и процесс синхронной смены на стороне Keycloak и прокси
  (zero-downtime — через graceful reload/rolling restart).
* Логаут: для решений без встроенного RP-initiated logout (vouch-proxy,
  "голый" Envoy) — отдельно проработать сценарий отзыва сессии
  пользователя (истечение cookie TTL, ручной logout-эндпоинт).
* Инцидент-плейбук: что делать при недоступности Keycloak — все
  рассмотренные решения в этом случае блокируют вход новым пользователям;
  уже залогиненные сессии продолжают работать до истечения cookie/access
  token (если refresh не настроен агрессивно) — учитывать при планировании
  окон обслуживания Keycloak.
* Версионирование конфигурации прокси и realm-экспорта Keycloak — через
  git, review перед выкаткой (особенно правила `resources`/RBAC).
