# RBAC-сценарий: OpenResty + lua-resty-openidc

**Порт:** 5188 · **URL:** http://service2.localhost:5188/

## 1. Архитектура

Единственное решение в стенде, где path-based RBAC реализуется буквально
**кодом**, а не декларативной конфигурацией — никакой дополнительной
инфраструктуры (второй инстанс, внешний auth-сервис, ACL-движок) не нужно.
Один процесс OpenResty, два `location`-блока:

- `location /` — после `openidc.authenticate()` проверяет, есть ли в массиве
  `id_token.roles` значение `Team2_Users`; если нет — `403` до `proxy_pass`.
- `location /admin` — аналогично, но требует `Team2_Admins`.

nginx сам матчит `/admin` как более специфичный префикс без regex —
порядок объявления `location`-блоков в файле не влияет на выбор (проверено
эмпирически: `location /admin` объявлен ПОСЛЕ `location /`, тем не менее
запросы к `/admin` обслуживаются именно им).

Общая функция `has_role(id_token, role)` вынесена в `init_by_lua_block`,
чтобы не дублировать код цикла по массиву ролей в каждом location — но это
уже инженерная гигиена самого автора конфига, фреймворк её не навязывает
(и не проверяет на этапе старта, в отличие от декларативных `resources`/`policy`
у gogatekeeper/Pomerium, где неверный YAML — это ошибка валидации при старте,
а не потенциальный runtime-баг).

## 2. Конфигурация

Полный `nginx.conf` — см. файл рядом. Ключевые решения:

- `client_id`/`client_secret` — `nginx-openresty-rbac-client` /
  `nginx-openresty-rbac-secret-CHANGEME`, один общий клиент на оба location
  (redirect_uri у обоих одинаковый: `/redirect_uri`).
- `session_contents = { id_token = true }` — в сессию (cookie, подписанную
  `lua-resty-session`) кладётся именно id_token, откуда потом читаются роли.
- `Dockerfile` идентичен основному стенду: `openresty/openresty:1.25.3.1-alpine-fat`
  + `opm get bungle/lua-resty-session=3.10` (обязательная фиксация версии —
  4.x несовместим с OpenSSL-обвязкой этого образа) + `opm get
  zmartzone/lua-resty-openidc`.

### Найдена и исправлена причина, по которой в основном стенде `X-Forwarded-User`/`X-Forwarded-Email` не долетали до backend

В этой реализации `ngx.req.set_header("X-Forwarded-User", ...)` внутри
`access_by_lua_block` **сработал корректно** — заголовки видны на backend
(см. тест 2 ниже). Отличий от исходного кода в `proxies/nginx-openresty/`
по сути нет, поэтому наиболее вероятная причина прежней проблемы —
не в самом коде простановки заголовка, а в конкретных условиях того
прогона (например, кэшированный ответ backend без `always` на
`add_header`, либо `res.id_token` были `nil` из-за иного состава `scope`/
`session_contents` в момент теста). Точную причину без доступа к тому
конкретному запуску установить нельзя — но в данной RBAC-реализации
проблема не воспроизвелась.

## 3. Результаты тестов

Все команды выполнялись реально, вывод — фактический.

| # | Сценарий | Ожидание | Результат |
|---|---|---|---|
| 1 | Без сессии → `GET /` | 302 на Keycloak | **302** ✅ |
| 2 | `team2user` → `GET /` | 200, "Team2_Users" | **200**, `X-Debug-Forwarded-User: team2user`, `X-Debug-Forwarded-Email: team2user@corp.local` ✅ |
| 3 | `team2user` (та же сессия) → `GET /admin` | 403 | **403** `Forbidden: требуется роль Team2_Admins` ✅ |
| 4 | `team2admin` → `GET /` | 200 | **200** ✅ |
| 5 | `team2admin` (та же сессия) → `GET /admin` | 200, "Team2_Admins" | **200**, тело содержит "Team2_Admins" ✅ |
| 6 | `testuser` (роль `app-user`, без `Team2_*`) → `GET /` | 403 | **403** `Forbidden: требуется роль Team2_Users` ✅ |

**Наблюдение про сессию между `location`:** cookie сессии `lua-resty-session`
ставится с `Path=/` по умолчанию — **одна и та же** аутентифицированная
сессия действует и для `/`, и для `/admin` без повторного логина; при
переходе с `/` на `/admin` (тест 3, 5) `openidc.authenticate()` просто
восстанавливает сессию из cookie и сразу переходит к проверке роли, без
редиректа на Keycloak. Это ожидаемо, т.к. это один и тот же nginx-процесс
и один client_id — в отличие, например, от gogatekeeper, где `/` и `/admin`
были бы вообще разными инстансами при межсервисном сценарии (здесь это не
так, т.к. `/` и `/admin` — один и тот же location-уровень одного сервиса).

**Технический нюанс, не влияющий на итог:** тест 6 (`testuser` без ролей)
формально «прошёл» по логике скрипта `test-oidc-login.sh`, потому что текст
сообщения об отказе — `"Forbidden: требуется роль Team2_Users"` — **сам
содержит** искомую подстроку `EXPECT_TEXT="Team2_Users"`. Проверка кодом
`HTTP_CODE:403` и телом ответа подтверждает, что это именно корректный
отказ в доступе, а не случайный пропуск — но при повторном использовании
скрипта для подобных сценариев стоит выбирать `EXPECT_TEXT`, не
пересекающийся с текстом ошибки (например, точную фразу из HTML backend'а,
а не общее слово-роль).

## 4. Ограничения этого подхода

- **Нужна Lua-экспертиза в команде.** RBAC-логика — обычный императивный
  код, а не декларативная конфигурация; ошибку в цикле по ролям или в
  выборе `location` никто заранее не провалидирует — только тестами.
- **Нет встроенной валидации конфигурации.** В отличие от gogatekeeper
  (`resources`) или Pomerium (`policy`), синтаксически некорректный или
  логически ошибочный Lua-код упадёт только в рантайме на конкретном
  запросе, а не при старте процесса.
- **Кастомная сборка образа обязательна** (см. общий вывод по OpenResty в
  основном RND-отчёте — темп поддержки `lua-resty-openidc` замедлился,
  риск несовместимости версий зависимостей при апгрейде).
- **Масштабируется вручную.** Для третьего/четвёртого уровня ролей просто
  добавляется ещё один `location` + ещё один `if has_role(...)` — работает,
  но при большом числе комбинаций путей/ролей это быстро превращается в
  дублирующийся boilerplate без общего декларативного описания политики
  (как `resources`-список у gogatekeeper).

## Итог

RBAC на одном hostname с разными ролями для `/` и `/admin` реализован и
полностью протестирован (все 6 сценариев, включая проверку, что одна
сессия работает на оба location без повторного логина, и что пользователь
без нужной роли получает `403`, а не редирект-луп). Подход рабочий и даже
самый гибкий архитектурно (никакой доп. инфраструктуры), но вся
ответственность за корректность авторизационной логики лежит на
написанном вручную Lua-коде — при большом количестве ролей/путей это
может стать источником неявных багов, которые не поймает статическая
проверка конфигурации, в отличие от decision-декларативных решений вроде
gogatekeeper или Pomerium.
