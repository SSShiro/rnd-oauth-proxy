# RBAC-сценарий: gogatekeeper

Path-based RBAC на одном домене `service2.localhost:5181`: корень `/`
требует роль `Team2_Users`, `/admin` — роль `Team2_Admins`. Реализовано
одним инстансом gogatekeeper перед общим `service2-backend` (без единой
строки авторизационной логики в самом backend).

## 1. Архитектура

gogatekeeper (community-продолжение Keycloak Gatekeeper / Louketo Proxy)
сразу совмещает роль reverse-proxy перед `service2-backend` и RBAC-движка —
никакого отдельного auth-сервиса, sidecar'а или Lua-кода не требуется, в
отличие от связок вида «прокси + внешний authz-сервис». Правила задаются
декларативно в секции `resources` конфига — список объектов `{uri, roles}`,
каждый превращается в отдельный HTTP-маршрут с цепочкой middleware,
проверяющей JWT-claim `roles` из access_token, выданного Keycloak (`realm
corp-sso`).

```yaml
resources:
  - uri: /admin
    roles: [Team2_Admins]
  - uri: /admin/*
    roles: [Team2_Admins]
  - uri: /*
    roles: [Team2_Users]
```

**Порядок правил и то, как он реально работает.** Задание для этого
сценария прямо предписывало проверить эмпирически расхожее утверждение
«gogatekeeper матчит `resources` в порядке объявления, первое совпадение
побеждает — специфичные правила обязаны идти раньше `/*`, иначе никогда не
сработают». Эксперимент (раздел 3, пункты «Порядок resources») **это
утверждение для gogatekeeper 4.11.0 не подтвердил**: при обратном порядке
(`/*` объявлен первым, `/admin` и `/admin/*` — после) `/admin` для
пользователя без роли `Team2_Admins` всё равно корректно вернул `403`, а не
ошибочно пропустил запрос. Причина — в исходном коде
(`pkg/keycloak/proxy/server.go`, функция построения роутера) каждый ресурс
регистрируется как самостоятельный HTTP-маршрут через `go-chi/chi`
(`hRouter.MethodFunc(method, res.URL, ...)`), а `chi` использует радиксное
дерево маршрутов и сам выбирает **наиболее специфичный** зарегистрированный
маршрут для входящего пути — независимо от того, в каком порядке маршруты
были зарегистрированы в YAML. Так что для этой конкретной версии/движка
порядок объявления `resources` не критичен для корректности матчинга.

Специфичное-перед-общим тем не менее оставлено в итоговом `config.yml` как
**defensive-практика**: во-первых, так конфиг читается человеком естественнее
(специфика сверху вниз); во-вторых, распространённый в документации и
статьях по (Keycloak) Gatekeeper совет про строгий порядок мог быть верен
для более старых форков/версий с иной (последовательной, не радиксной)
реализацией матчинга, и полагаться на недокументированную деталь текущей
реализации `chi` в проде рискованно — если внутренний движок матчинга
когда-нибудь сменится на строго порядковый, конфиг с правильным порядком
продолжит работать, а конфиг с обратным — сломается тихо и незаметно.

**Второй, куда более значимый и подтверждённый на практике нюанс** —
паттерн `/admin/*` (в терминах `chi` — wildcard-маршрут) не матчит
литеральный путь `/admin` **без завершающего слэша**: такой запрос
проваливается в catch-all `/*` и требует только `Team2_Users`, полностью
обходя защиту `Team2_Admins`. Это подтверждено вживую (раздел 3, пункт
«Дополнительный эксперимент: `/admin/*` без явного `/admin`»): без отдельного
правила `uri: /admin` пользователь `team2user` (без роли `Team2_Admins`)
получал `HTTP 200` на `GET /admin`. Поэтому в `config.yml` два правила на
admin-раздел: `/admin` (точный путь) и `/admin/*` (всё под ним).

## 2. Конфигурация

- [`docker-compose.yml`](docker-compose.yml) — образ
  `quay.io/gogatekeeper/gatekeeper:4.11.0`, контейнер `gogatekeeper-rbac`,
  порт `5181:5181`, сеть `oauth-net` (`external: true, name: oauth-net`,
  сеть уже создана корневым `docker-compose.yml` проекта).
- [`config.yml`](config.yml) — итоговый конфиг:

```yaml
discovery-url: http://keycloak:8080/realms/corp-sso   # OIDC discovery Keycloak, realm corp-sso
client-id: gogatekeeper-rbac-client
client-secret: gogatekeeper-rbac-secret-CHANGEME

listen: 0.0.0.0:5181
upstream-url: http://service2-backend:80               # backend без своей authz-логики

redirection-url: http://service2.localhost:5181        # gatekeeper сам добавит /oauth/callback;
                                                         # итог должен совпасть с redirect_uri в Keycloak-клиенте

encryption-key: "ZD28bZsid2tk8mbrNJE6qQoX9lmCC2Bh"      # 32 символа, шифрование cookie-сессии
secure-cookie: false                                    # стенд на http://, без TLS
enable-default-deny: false                               # ОБЯЗАТЕЛЬНО при собственных resources —
                                                          # иначе конфликт "you've enabled default deny
                                                          # and at the same time defined own rules for /*"
                                                          # и crash-loop при старте
enable-refresh-tokens: true

resources:
  - uri: /admin        # точный путь /admin (без слэша) — см. раздел 1, найденный нюанс
    roles:
      - Team2_Admins
  - uri: /admin/*       # всё остальное под /admin/
    roles:
      - Team2_Admins
  - uri: /*             # catch-all — остальной сайт, включая корень /
    roles:
      - Team2_Users
```

### Эксперимент: порядок `resources` (обязательный пункт задания)

Конфиг временно изменён на обратный порядок (`/*` объявлен ПЕРВЫМ, `/admin`
и `/admin/*` — после), контейнер перезапущен (`docker restart
gogatekeeper-rbac`), в лог-строке `protecting resource` подтверждён факт
регистрации в изменённом порядке. Затем — свежий логин `team2user` (без
роли `Team2_Admins`) и запрос `/admin` той же сессией.

```yaml
resources:                 # ЭКСПЕРИМЕНТ — намеренно неверный (обратный) порядок
  - uri: /*
    roles: [Team2_Users]
  - uri: /admin
    roles: [Team2_Admins]
  - uri: /admin/*
    roles: [Team2_Admins]
```

```
$ curl -s -b /tmp/team2user_wrongorder.jar -o /tmp/wo2.html -w "%{http_code}\n" http://service2.localhost:5181/admin
403
$ curl -s -b /tmp/team2user_wrongorder.jar -o /tmp/wo3.html -w "%{http_code}\n" http://service2.localhost:5181/admin/
403
```

Строка из лога gogatekeeper (`docker logs gogatekeeper-rbac`) для этого
запроса:
```
{"path":"/admin","access":"denied","userID":"e7a8c377-...","resource":"/admin","roles":"Team2_Admins"}
{"path":"/admin","status":403}
```

**Фактический результат: `403`, доступ корректно ЗАБЛОКИРОВАН, несмотря на
обратный порядок правил.** Это расходится с гипотезой задания («при
неправильном порядке тест на `/admin` НЕПРАВИЛЬНО проходит»). Объяснение —
см. раздел 1: gogatekeeper 4.11.0 регистрирует каждый `resources`-элемент
как отдельный маршрут в `go-chi/chi`-роутере (радиксное дерево), который
сам выбирает наиболее специфичный маршрут независимо от порядка
регистрации. После эксперимента конфиг возвращён к исходному
(специфичное-перед-общим) порядку, и контейнер перезапущен; повторная
проверка (`team2user` → `/admin`) снова дала `403` — поведение не
изменилось, что подтверждает: для данной версии порядок не влияет на
результат ни в одну, ни в другую сторону.

Итог по заданию — **эмпирическая проверка проведена, оба результата
зафиксированы**, но реальный вывод оказался не тем, что предполагался
изначально: важность строгого порядка правил для gogatekeeper 4.11.0 не
подтвердилась.

### Дополнительный эксперимент: `/admin/*` без явного `/admin`

Проведён параллельно, поскольку по ходу работы обнаружился реальный
security-gap, не связанный с порядком. Конфиг временно урезан до двух
правил (без отдельного `uri: /admin`):

```yaml
resources:
  - uri: /admin/*
    roles: [Team2_Admins]
  - uri: /*
    roles: [Team2_Users]
```

```
$ curl -s -b /tmp/team2user_final.jar -o /tmp/onlyadmin_admin.html -w "HTTP status: %{http_code}\n" http://service2.localhost:5181/admin
HTTP status: 200
```

Лог gogatekeeper по этому запросу:
```
{"path":"/admin","access":"permitted","resource":"/*","status":200}
```

Пользователь `team2user` **без роли `Team2_Admins`** получил `200` и
содержимое `/admin` (`административная область`) — RBAC полностью обойдён,
потому что `chi` не матчит wildcard-маршрут `/admin/*` на путь `/admin` без
завершающего слэша, запрос проваливается в catch-all `/*`, для которого
достаточно роли `Team2_Users`. После добавления обратно явного правила `uri:
/admin` — повторная проверка снова `403` для `team2user` и `200` для
`team2admin`. Именно поэтому итоговый `config.yml` содержит оба правила
(`/admin` и `/admin/*`).

## 4. Ограничения

- **`/admin/*` не покрывает литеральный путь `/admin`.** Это подтверждённая
  и куда более практически опасная находка, чем гипотеза про порядок
  правил (см. раздел 3): если защищать только wildcard-паттерн
  `/some/path/*`, точный путь `/some/path` (без хвостового слэша) остаётся
  незащищённым и провалится в менее строгое catch-all-правило. Нужно
  закладывать в чек-лист ревью подобных RBAC-конфигов: на каждый
  защищаемый "раздел" — два правила, точный путь и `путь/*`, либо
  единообразная политика редиректов на канонический URL с хвостовым слэшем
  ДО прохождения через RBAC-проверку.
- **Порядок `resources` в gogatekeeper 4.11.0 эмпирически не критичен**
  (движок матчинга на `go-chi/chi` сам выбирает наиболее специфичный
  маршрут), но полагаться на эту недокументированную деталь текущей
  реализации не стоит — она может измениться в будущих версиях или не
  выполняться в других форках/используемых образах. Специфичное-перед-общим
  остаётся правильной практикой конфигурирования, даже если формально
  необязательна здесь и сейчас.
- **Один upstream на инстанс.** gogatekeeper не делает host- или
  path-based роутинг на несколько разных backend-сервисов из одного
  процесса — весь конфиг (`upstream-url`, `client-id`/`secret`,
  `redirection-url`, `listen`) относится ровно к одному защищаемому
  сервису. Если бы в этом же RND-стенде понадобился ещё и отдельный
  `service1` на другом домене/порту с более простой (без ролей) схемой
  авторизации — это был бы отдельный инстанс gogatekeeper со своим
  контейнером, своим портом, своим клиентом в Keycloak и своим
  `config.yml`, а не дополнительная секция в этом же файле.
- В образе включён PKCE (`enable-pkce: true` по умолчанию) — Keycloak уже
  поддерживает это без дополнительной настройки клиента, но при переносе на
  другой IdP это стоит проверить явно.
- `secure-cookie: false` и HTTP (не HTTPS) — годится только для локального
  RND-стенда; в проде обязательны TLS и `secure-cookie: true`.

---

**Итог:** gogatekeeper реализует path-based RBAC полностью декларативно —
три поля YAML на правило, без отдельных auth-сервисов, без Lua/плагинов. Все
6 пунктов тестовой матрицы пройдены. Обязательный эксперимент с порядком
`resources` проведён и зафиксирован, но его реальный результат опроверг
исходную гипотезу: для gogatekeeper 4.11.0 (роутинг на `go-chi/chi`) порядок
объявления правил не влияет на корректность матчинга — движок сам находит
наиболее специфичный маршрут. Единственная реально подтверждённая и
практически значимая находка — паттерн `/admin/*` не матчит путь `/admin`
без завершающего слэша и требует отдельного точного правила; это стоит
закладывать в чек-лист ревью подобных конфигов на любой версии/форке.
